📋 Software Requirements Specification (SRS)
This document defines the complete requirements for the MERN CRUD Student Management System built throughout this course. Read it before you start coding.

01 · Introduction

Purpose

The purpose of this document is to describe the complete software requirements for the MERN CRUD Student Management System — a full-stack web application built using MongoDB, Express.js, React, and Node.js. The system provides an online platform for managing student records through Create, Read, Update, and Delete (CRUD) operations.

Project Objectives

  • 1
    Build a fully functional full-stack application using the MERN stack from scratch.
  • 2
    Allow users to add, view, update, and delete student records through a clean web interface.
  • 3
    Implement a RESTful API backend with proper validation, error handling, and HTTP status codes.
  • 4
    Deploy the completed application to production using Render (backend) and Vercel (frontend).
  • 5
    Demonstrate real-world software development practices: MVC architecture, clean code, and version control.

Scope

The system will manage student records for a single organization. The scope includes:

In Scope
  • Full CRUD for student records
  • REST API with 5 endpoints
  • React frontend with forms & tables
  • MongoDB Atlas data storage
  • Input validation & error handling
  • Production deployment
Out of Scope
  • User authentication & login
  • Role-based access control
  • File / image uploads
  • Real-time updates (WebSockets)
  • Pagination & search filters
  • Payment or billing features

02 · Stakeholders

The following individuals and groups interact with or are affected by the system:

Administrator

Manages all student records, has full CRUD access, and maintains the system.

Student

Has their data stored in the system. Does not directly interact with the app in this version.

Visitor

Can browse the student list without making changes (read-only access).

Business Owner

Commissioned the system; defines requirements and reviews final deliverables.

Developer

Builds and maintains the application; follows this SRS as the authoritative reference.

Course Instructor

Supervises the project, evaluates deliverables, and provides feedback.

05 · Non-Functional Requirements

Non-functional requirements define how well the system performs its functions.

Performance
  • API responses must complete in under 500 ms under normal load.
  • Frontend initial page load must be under 3 seconds on a standard connection.
  • The system must handle at least 100 concurrent users without degradation.
Security
  • All secrets (DB passwords, API keys) must be stored in .env files — never in code.
  • HTTPS must be enforced in the production environment.
  • Input must be sanitised to prevent NoSQL injection and XSS attacks.
Usability
  • The frontend must be fully responsive across mobile, tablet, and desktop.
  • Navigation must be intuitive — no training required for basic operations.
  • All forms must provide clear validation feedback messages.
Reliability
  • Target system uptime of 99.9% in production.
  • MongoDB Atlas provides automatic backups and replication.
  • All unhandled errors must be caught and return a structured JSON error response.
Maintainability
  • Code must follow MVC architecture with clear folder separation.
  • Functions must be small, named descriptively, and each serve one purpose.
  • The project must include a README.md with setup instructions.
Compatibility
  • Must work on Chrome, Firefox, Edge, and Safari (latest versions).
  • Application must run on Windows, macOS, and Linux development machines.
  • Node.js version v18 LTS or higher required.

08 · System Constraints

The following limitations and restrictions apply to this project.

Budget
The project uses only free-tier services: MongoDB Atlas (512 MB), Render (free tier with cold starts), and Vercel (free tier).
Timeline
The complete application must be built and deployed within the duration of the 10-module course (~10 hours of study).
Browser Compatibility
Only modern browsers are supported. Internet Explorer is explicitly excluded.
Third-Party APIs
The system depends on MongoDB Atlas availability. Any Atlas outage will make the API unavailable.
No Authentication
User authentication is out of scope for this version. All CRUD operations are publicly accessible (suitable for a learning environment only).
Single Data Entity
This version manages only the Student entity. Multi-entity relationships are deferred to future iterations.

09 · Assumptions

The following conditions are assumed to be true throughout the development and operation of the system.

  • All users have a stable internet connection capable of accessing web applications.
  • Users possess basic computer skills — they can navigate a browser, fill forms, and click buttons.
  • MongoDB Atlas cloud services remain available and free-tier limits are not exceeded during development.
  • Users access the application using a modern web browser (Chrome, Firefox, Edge, or Safari).
  • The development team has working installations of Node.js v18+, Git, and VS Code before starting Module 2.
  • Render and Vercel free-tier hosting plans remain available with sufficient resources for course demonstrations.

10 · Business Rules

Business rules are constraints that govern system behaviour regardless of technical implementation.

BR-01
Unique Email Address

Each student must have a unique email address. The system will reject any attempt to register a duplicate email.

BR-02
Required Fields

Name, email, and course are mandatory. A student record cannot be saved with any of these fields empty.

BR-03
Valid Age Range

If age is provided, it must be a positive number between 1 and 120. Negative or unrealistic ages are rejected.

BR-04
Approved Course Values

The course field must be one of the pre-defined values (e.g., IT, CS, SE, IS). Free-text course names are not allowed.

BR-05
Deletion Confirmation

A student record cannot be deleted without explicit user confirmation. Accidental deletion must be prevented at the UI level.

BR-06
Secrets in Environment Variables

Database connection strings, API keys, and other sensitive data must never be hardcoded. They must be stored in .env files excluded from version control.

13 · Interface Requirements

User Interface (UI)
  • Built with React 18 and Bootstrap 5
  • Responsive layout — mobile-first design
  • Student list displayed in a sortable data table
  • Add / Edit forms with real-time validation feedback
  • Success and error toast notifications
Database Interface
  • Mongoose ODM connects Node.js to MongoDB Atlas
  • Connection string stored in MONGO_URI environment variable
  • Connection pooling handled automatically by Mongoose
Frontend–Backend Interface
  • React uses Axios to call Express API endpoints
  • All requests and responses use JSON format
  • CORS configured in Express to allow the React dev server origin
  • Base API URL stored in VITE_API_URL environment variable
External Services
  • MongoDB Atlas — cloud database hosting
  • Render — backend (Node.js/Express) deployment
  • Vercel — frontend (React/Vite) deployment
  • No email or payment gateway integration in v1

14 · Security Requirements

SR-01
Environment Variables

All credentials and secrets must be stored in .env files. The .env file must be listed in .gitignore to prevent accidental exposure.

SR-02
Input Validation

All user input must be validated on both the client side (React) and server side (Express + Mongoose) before being saved to the database.

SR-03
HTTPS in Production

Both the frontend (Vercel) and backend (Render) must serve traffic exclusively over HTTPS. HTTP connections must be redirected.

SR-04
CORS Policy

The Express server must restrict cross-origin requests to the approved frontend domain only. Wildcard * origins must not be used in production.

SR-05
NoSQL Injection Prevention

Mongoose's schema-based casting inherently sanitises inputs. Additional middleware (e.g., express-mongo-sanitize) should be added for production.

SR-06
Error Message Safety

In production, stack traces and internal error details must never be exposed to the client. All errors must return a generic user-safe message.

15 · Acceptance Criteria

The project will be considered complete when all of the following criteria are verified.

AC-01
Student List Displays Correctly

The homepage renders a table of all student records fetched from the MongoDB database via the Express API.

AC-02
Create Student Works

Submitting the Add Student form with valid data inserts a new document in MongoDB and immediately reflects in the student list.

AC-03
Edit Student Works

Clicking Edit pre-fills the form with current values. Saving the form updates the document in MongoDB via PUT.

AC-04
Delete Student Works

Confirming the delete prompt removes the student from MongoDB and removes them from the UI list immediately.

AC-05
Validation Prevents Bad Data

Submitting the form with an empty required field or an invalid email shows an error message and does not save to the database.

AC-06
Duplicate Email Rejected

Trying to add a student with an email that already exists in the database returns a 400 error with a clear message.

AC-07
API Returns Correct Status Codes

All five CRUD endpoints return the appropriate HTTP status codes (200, 201, 400, 404, 500) verified through Postman.

AC-08
Application is Responsive

The UI renders correctly and all interactions work on mobile (≤ 375px), tablet (≤ 768px), and desktop (≥ 1024px) viewports.

AC-09
Deployed to Production

The backend is live on Render and the frontend is live on Vercel. Both production URLs are accessible publicly over HTTPS.

AC-10
No Secrets in Source Code

A code review confirms that no API keys, passwords, or connection strings are hardcoded anywhere in the repository.
